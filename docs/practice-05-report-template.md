# Звіт до практичної роботи №5
## SQLite, користувачі та автентифікація цифрового деканату

### 1. Мета та власний результат

Мета роботи — реалізувати збереження даних користувачів у SQLite, захист паролів за допомогою PBKDF2-HMAC-SHA256 та API-операції реєстрації, видалення, блокування й перевірки облікових даних.

Роботу виконано у форку `digital-dean-api-starter`:

- Репозиторій: https://github.com/Saymonga/digital-dean-api-starter
- Робоча гілка: `practice-05`
- Початковий анотований тег: `practice-05-base`
- Фінальний тег: `practice-05` (створюється після завершення роботи).

У межах роботи реалізовано:
- ініціалізацію SQLite та довідкових даних;
- зберігання паролів у вигляді похідних значень PBKDF2 із сіллю;
- репозиторій для роботи з користувачами;
- чотири API-операції;
- автоматизовані тести бази даних, паролів та API.

### 2. Середовище та база даних

Використане середовище:

| Компонент | Версія |
|---|---|
| Python | 3.14.3 |
| SQLite | 3.50.4 |
| FastAPI | 0.162.0 |
| Pydantic | 2.14.2 |

У базі даних створено шість таблиць:

1. `status` — довідник статусів користувачів.
2. `user` — облікові записи користувачів.
3. `role` — довідник ролей.
4. `user_role` — зв'язок користувачів із ролями.
5. `course` — навчальні курси.
6. `grade` — оцінки студентів.

Основні зв'язки:
- `user.status_id` посилається на `status.id`;
- `user_role.user_id` посилається на `user.id`;
- `user_role.role_id` посилається на `role.id`;
- `grade.student_id` і `grade.teacher_id` посилаються на `user.id`;
- `grade.course_id` посилається на `course.id`.

У таблиці `user_role` використовується складений первинний ключ. У таблиці `grade` первинний ключ складається з `student_id` та `course_id`. Для оцінки встановлено обмеження діапазону від 0 до 100.

Довідник статусів:
- `0` — inactive;
- `1` — active;
- `2` — blocked.

Довідник ролей:
- `1` — admin;
- `2` — manager;
- `3` — teacher;
- `4` — student.

Ініціалізація виконується транзакційно. Для довідкових записів використовується `ON CONFLICT(id) DO NOTHING`, а після ініціалізації перевіряється відповідність довідників очікуваним значенням.

Повторний запуск команди:

`python -m app.db.initialize`

завершився повідомленням:

`Database initialized; no default accounts created.`

Це підтверджує успішне виконання ініціалізації. Файл бази даних до Git не додавався.

### 3. Захист паролів

Для захисту паролів використовується PBKDF2-HMAC-SHA256.

Параметри реалізованого профілю:

| Параметр | Значення |
|---|---|
| Алгоритм | PBKDF2-HMAC-SHA256 |
| Кількість ітерацій | 600 000 |
| Довжина солі | 16 байтів |
| Довжина результату | 32 байти |
| Мінімальна довжина пароля | 15 символів |
| Максимальна довжина пароля | 128 символів |
| Максимальний розмір UTF-8 | 512 байтів |

Сіль генерується випадково за допомогою `secrets.token_bytes`. Для кожного пароля використовується окрема сіль.

Результат зберігається у форматі:

`pbkdf2_sha256$600000$<hex-представлення результату>`

Сіль зберігається окремо в шістнадцятковому форматі.

Під час перевірки пароля:
- використовується точне UTF-8-кодування;
- не виконується автоматичне обрізання пробілів або зміна регістру;
- перевіряється коректність формату запису та параметрів;
- порівняння виконується через `hmac.compare_digest`.

Для однакового вигаданого пароля різні випадкові солі дають різні результати похідного значення. Це ускладнює виявлення однакових паролів за їхніми збереженими значеннями.

Цей механізм не шифрує файл SQLite і не захищає базу від фізичного копіювання. Він призначений для безпечнішого зберігання паролів.

### 4. Реалізація API

Реалізовано чотири операції.

| Метод | Шлях | Призначення | Успішний код |
|---|---|---|---|
| POST | `/api/v1/users` | Реєстрація користувача | 201 |
| DELETE | `/api/v1/users/{user_id}` | Видалення користувача | 204 |
| PATCH | `/api/v1/users/{user_id}/block` | Блокування користувача | 200 |
| POST | `/api/v1/auth/login` | Перевірка облікових даних | 200 |

Реєстрація створює користувача та повертає безпечні поля облікового запису без пароля й солі.

Видалення користувача повертає `204 No Content` без тіла відповіді.

Блокування змінює статус користувача на `blocked`. Повторне блокування вже заблокованого користувача є ідемпотентним.

Операція входу повертає JSON-значення `true` або `false`. Вхід дозволяється лише користувачам зі статусом `active`.

Для помилкових ситуацій передбачені відповідні коди:
- `404` — користувача не знайдено;
- `409` — конфлікт даних, наприклад повторна реєстрація;
- `422` — помилка валідації;
- `500` — внутрішня помилка операції з базою даних.

Повідомлення про внутрішні помилки не повинні розкривати паролі, сіль або внутрішні дані облікового запису.

### 5. Перевірки

Автоматизовані перевірки виконувалися за допомогою `pytest`.

Окремо запускалися:
- `tests/test_practice05_database.py`;
- `tests/test_practice05_passwords.py`;
- `tests/test_practice05_accounts.py`.

Усі зазначені групи тестів завершилися успішно. Також було виконано повний запуск тестового набору проєкту командою:

`pytest -q`

Повний запуск завершився успішно.

Для ручної перевірки API використовувався Swagger UI за адресою:

`http://127.0.0.1:8000/docs`

Postman не використовувався.

Фактично спостережені результати ручної перевірки:

| Операція | Результат |
|---|---|
| Реєстрація тестового користувача | `201 Created` |
| Вхід неактивного користувача | `200 OK`, значення `false` |
| Блокування користувача | `200 OK`, `status_id: 2` |
| Видалення користувача | `204 No Content` |

Під час першої спроби реєстрації було отримано `500 Internal Server Error`. Після окремого запуску ініціалізації бази даних повторна реєстрація завершилася успішно з кодом `201`.

Для ручної перевірки використовувався синтетичний тестовий обліковий запис. Його було видалено після перевірки.

Автоматичні тести охоплюють роботу бази даних, захист паролів та API. Ручні перевірки виконувалися через Swagger UI.

### 7. Висновки та межі застосування

У ході практичної роботи реалізовано SQLite-схему цифрового деканату, механізм захисту паролів та API-операції керування користувачами.

Повторна ініціалізація бази даних не повинна призводити до дублювання довідкових записів.

Використання PBKDF2 із випадковою сіллю підвищує стійкість збереження паролів, однак не є шифруванням усієї бази даних.

Роль користувача не є тотожною його статусу. Наявність зовнішнього ключа на користувача не перевіряє, чи має він роль викладача.

Метод входу повертає лише булевий результат і не створює сесію та не забезпечує авторизацію адміністративних методів.

Розроблений сервер призначений для локального використання. Для промислового застосування потрібні додаткові механізми автентифікації, авторизації, керування сесіями та захисту інфраструктури.

### 9. Глосарій

- **API (Application Programming Interface)** — програмний інтерфейс взаємодії між компонентами програмного забезпечення.
- **CRUD (Create, Read, Update, Delete)** — базові операції створення, читання, оновлення та видалення даних.
- **FK (Foreign Key)** — зовнішній ключ, що забезпечує зв'язок між таблицями.
- **HMAC (Hash-based Message Authentication Code)** — код автентифікації повідомлення на основі хеш-функції.
- **HTTP (Hypertext Transfer Protocol)** — протокол передавання даних у вебсистемах.
- **JSON (JavaScript Object Notation)** — текстовий формат обміну структурованими даними.
- **PBKDF2 (Password-Based Key Derivation Function 2)** — алгоритм отримання похідного значення з пароля.
- **PK (Primary Key)** — первинний ключ таблиці.
- **pytest** — інструмент автоматизованого тестування Python-застосунків.
- **SQLite** — вбудована реляційна система керування базами даних.
- **UTF-8** — стандарт кодування символів Unicode.
